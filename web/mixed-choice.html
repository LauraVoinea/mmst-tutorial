Mixed choice

Mixed choice in asynchronous multiparty session types: participants' views may diverge for a while, and can always reach a consistent state.

projection

One global protocol, projected onto one local type per role (§4.2). ⊕ send, & receive, ▷ between the two sides of a mixed choice, both live at once.

why mixed choice

Classical multiparty session types (Honda, Yoshida, Carbone, POPL 2008) need directed choice: one named role decides, and a role only sends or only receives. Exceptions (Carbone, Honda, Yoshida, CONCUR 2008), interruptible blocks (Demangeon, Honda, Hu, Neykova, Yoshida, FMSD 2015), timeouts (Pears, Bocchi, King, COORDINATION 2023; Hou, Lagaillardie, Yoshida, ECOOP 2024) and crash handling (Viering, Chen, Eugster, Hu, Ziarek, ESOP 2018; Viering, Hu, Eugster, Ziarek, OOPSLA 2021) each added a bespoke construct (Appendix A). Each is a role facing input and output at once. Mixed choice (MC) covers them; the paper's Table 1 re-expresses them.

the construct

mixed {                  // left: the default
    a1() from A to B;
    a3() from B to C;
} or A -> B {            // right: B may overrule A
    TOa() from B to A;
    TOc() from B to C;
}

Both sides are live until someone commits, so two roles may speculate on different sides, which classical MST rules out: permitted here, and still statically checked (§2.1).

two runs

Timeout, the paper's Figure 1: B follows A (left) or overrules it (right).

Left: B commits by receiving a1; the others follow. Right: B commits by sending TOa; a1, already in flight, crosses it and is dropped by each runtime, using local information only.

the observer

The sender on the right is the MC's observer: the one role that may overrule (§2.1). The left is the speculative default; the others learn the outcome from what arrives. A fully symmetric construct would not be statically checkable; this asymmetric one is, and still expresses timeouts, cancellation, interrupts, heartbeats and graceful shutdown.

commitment and stale messages

The observer commits with its first action in the MC: receiving on the left, sending on the right. Another role commits on an action causally dependent on the observer's. Roles may disagree for a while; the checks guarantee they can always reach a consistent state.

In-flight messages from the side not taken are stale. Each runtime purges them using local information only, so application code never sees them: garbage collection, for messages (§4.1).

the four checks

One error can fail two checks: fix the first FAIL. A protocol can pass all four and still fail projection (§4.2, Couldn't project to R): the classical merge failure, unrelated to MC.

guarantees

Asynchronous, with FIFO order between any two roles. For an aware, balanced protocol: progress (Theorem 3.13, §3.3), operational correspondence between the global type and its projections, modulo stale messages (Theorem 4.4), and orphan-message freedom (Theorem 4.7, §4.4).

The generated Erlang keeps them: per role, a gen_<role>.erl gen_statem behaviour, correct by construction and not for editing, which handles commitment, switching sides and purging; and a <role>.erl template for your logic (§2.2).
